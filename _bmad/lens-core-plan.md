# Lens Core Module Plan

## Vision

**Lens Core** is the governance enforcement foundation for the Control Repo + Redirect Pattern architecture. It provides a bedrock agent that validates workspace structure, generates `.github/` enforcement files, and defines the Agents.md contract that all future Lens Core agents inherit from.

**Primary User:** System architects and governance administrators setting up Lens Core workspaces; agents and workflows built on top of this module.

**Why it matters:** The Lens Core architecture (Control Repo, TargetProjects, stub redirection, governance rules) is powerful but requires consistent enforcement. This module is the enforcement engine — ensuring all workspaces follow the constructs and enabling future agents to build on a reliable foundation.

## Ideas Captured (Ideation Complete)

**MVP Scope Locked:** For v1, we're delivering the **`lc-core-repo` enforcement agent** — the bedrock that validates and enforces Lens Core structural constructs across workspaces.

**Key Artifacts:**
- **Agent:** `lc-core-repo` with 6 enforcement/generation capabilities
- **`Agents.md` file:** The definitive governance contract specifying the Lens Core constructs that all future agents inherit from
- **`.github/` generation:** On `bmad-installer` invocation, generates redirect stubs and enforcement workflows
- **Extensibility hooks:** Future agents register custom rules in `rules-extension-points.md`

**Why this MVP scope:**
- Establishes the governance foundation that all future Lens Core agents depend on
- Creates the publishing pipeline (GitHub Action on push to develop)
- Validates the enforcement pattern works end-to-end
- Achievable, publishable, and foundational to everything else

**The `Agents.md` Role:**
- Definitive spec of Lens Core constructs (Control Repo, TargetProjects, stub redirection, naming, etc.)
- Contract that future agents reference when building on this foundation
- Generated by `lc-core-repo` during initialization
- Stable and rarely changed (governance changes are major events)

## Architecture

**Single bedrock enforcement agent (`lc-core-repo`)** that validates and enforces the Lens Core structural constructs across workspaces.

**Why single agent:**
- All future agents and workflows in Lens Core depend on this foundation — it must be definitive and unchanging
- Enforcement logic must be centralized for consistency
- Other agents inherit/extend capabilities from this core, they don't replace it
- Simpler governance model: one source of truth for the rules

**Core responsibilities:**
- Enforce Control Repo structure and naming conventions
- Validate TargetProjects layout and organization
- Generate `.github/` redirect stubs pointing to canonical `lens.core/` skills
- Generate enforcement workflows that run on repo operations
- Define and validate the `.lens` governance configuration
- Act as the extensible base for all other Lens Core agents

### Memory Architecture

**Shared enforcement rules + extensibility hooks** — the agent maintains:
- The definitive rule set that it enforces
- Extensibility points where future agents can register additional rules
- A log of enforcement actions for audit

**Memory structure:**
- `rules-core.md` — definitive structural rules (immutable for this agent)
- `rules-extension-points.md` — where future agents can hook custom rules
- `github-templates/` — templates for generated `.github/` files (redirect stubs, workflows)
- `enforcement-log/` — audit trail of validation and generation actions
- `index.md` — governance index

### Memory Contract

| File | Purpose | Agent Reads | Agent Writes | Content |
|------|---------|-------------|--------------|---------|
| `rules-core.md` | Definitive Lens Core rules | Read always | Rarely updated (major governance changes) | Control Repo structure, TargetProjects layout, naming, `.lens` schema |
| `rules-extension-points.md` | Hooks for other agents | Read on activation | Updated when new agents extend | Extensibility mechanism for future agents |
| `github-templates/redirect-stub.md` | Template for `.github` redirect stubs | Read before generation | N/A | The stubs that point to canonical `lens.core/` |
| `github-templates/workflows.md` | Template for enforcement workflows | Read before generation | N/A | Workflow definitions for runtime enforcement |
| `enforcement-log/YYYY-MM-DD.md` | Audit trail | Append | Append validation/generation events | Who, what, when for governance actions |
| `index.md` | Governance index | Read on activation | Update monthly | Quick reference to all rules and extensions |

### Cross-Agent Patterns

**Extensibility architecture:** Other agents inherit from this core:
- Future `lc-agent-*` agents read `rules-core.md` to understand the foundation
- They register custom rules/hooks in `rules-extension-points.md`
- They inherit the enforcement pattern from `lc-core-repo`
- The agent is the **bedrock skill** that all others build on top of

**Generation as enforcement:** When an agent (or user via `bmad-installer`) invokes this agent:
- It generates the required `.github/` structure
- It validates the workspace against `rules-core.md`
- Future agents can extend validation without changing the core

## Skills

### lc-core-repo

**Type:** Agent

**Persona:** Governance architect and enforcement engine. Authoritative, precise, detail-oriented. Knows the rules inside-out and applies them consistently. Explains *why* a rule exists and what it protects. This is the canonical rule source for the workspace.

**Core Outcome:** Every workspace enforces the Lens Core structural constructs, and every agent built on top of this foundation has a reliable, extensible rule engine to inherit from.

**The Non-Negotiable:** Correctness and consistency. Rules must be applied uniformly, generated files must be accurate, and the rule set must be the single source of truth. Hallucinations here cascade to every future agent.

**Capabilities:**

| Capability | Outcome | Inputs | Outputs |
|-----------|---------|--------|---------|
| **Validate Workspace Structure** | User/system knows if a workspace complies with Lens Core constructs | Workspace path; optional: specific rules to check | Validation report (structure diagram, pass/fail per rule, remediation guidance) |
| **Generate `.github` Redirect Stubs** | A repo has the correct redirect stubs pointing to canonical `lens.core/` | Control Repo path; Skill/workflow name to redirect | Generated `.github/workflows/` and `.github/prompts/` files (thin stubs with redirects) |
| **Generate Enforcement Workflows** | Repos have runtime enforcement (validations on push, PR, etc.) | Workspace config; desired enforcement rules | GitHub workflow files that run validation checks |
| **Define Core Rules** | Other agents understand what's required and extensible | (implicit) | `Agents.md` — the definitive rule document; ruleset in structured form |
| **Register Rule Extensions** | Future agents can add custom rules without modifying core | Extension spec (name, rules, constraints) | Registered extension added to extensibility registry |
| **Audit Enforcement** | System maintains compliance trail | (implicit) | Enforcement log showing all validation/generation actions |

**Memory:**
- **Reads on activation:** `rules-core.md`, `rules-extension-points.md`, `github-templates/*`, `index.md`
- **Writes:** Append to `enforcement-log/YYYY-MM-DD.md` with each validation or generation event; update `index.md` when extensions are registered
- **Init responsibility:** On first run, create all memory files from templates; generate the `Agents.md` file that documents the core rules

**Activation Modes:** Interactive (query/validate/generate on demand) + Headless (called by `bmad-installer` for automated setup)

**Tool Dependencies:** 
- File system access to read workspace structure
- Ability to generate and write files to `.github/`
- Optional: Git API for validation (not MVP)

**Design Notes:**
- **Separation of concerns:** This agent *enforces rules* but doesn't *decide* them. Rules are defined in memory and inherited by convention. Future agents extending this must update `rules-extension-points.md`.
- **Idempotency:** Running validation or generation multiple times produces the same result — safe to run repeatedly.
- **Generation is immutable for core files:** The redirect stubs and base workflows generated by this agent should not be manually edited. Extensions happen in `rules-extension-points.md`, not by hand-editing generated files.
- **The `Agents.md` file is the contract:** This is the definitive spec that all future Lens Core agents reference. It documents the constructs, the rules, and the extensibility pattern. It should be comprehensive, clear, and stable.

**Relationships:** This is the **bedrock agent**. All future `lc-agent-*` agents inherit from this one:
- They read `rules-core.md` on activation
- They register extensions in `rules-extension-points.md` if adding custom rules
- They inherit the enforcement pattern and memory architecture
- Other modules built on Lens Core will depend on this agent being correct

- Create the agent with all 6 capabilities

- `lc-agent-workspace-guide` — conversational interface to the rules
- `lc-agent-governance-validator` — active compliance checking
- Other domain-specific agents that inherit from this core
